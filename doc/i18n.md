# Internationalization

## Current locales

The UI ships with complete dictionaries for:

- English (`en`)
- Spanish (`es`)
- Portuguese (`pt`)

Locale data lives in `src/i18n/messages.ts`.

## Client behavior

On first load, the browser tries to use:

1. The saved locale from `localStorage`.
2. The browser language prefix, such as `es` from `es-MX`.
3. English as fallback.

The selected language is persisted in `localStorage` under `infernal-gibberlink-locale`.

## Adding a locale

1. Add the locale code to the `locales` tuple.
2. Add a display name in `localeLabels`.
3. Add a full dictionary under `messages`.
4. TypeScript will enforce the same keys as English through the `satisfies` constraint.

Example:

```ts
export const locales = ["en", "es", "pt", "de"] as const;
```

Then add `de` to `localeLabels` and `messages`.

## Translation scope

All user-facing application labels, status messages, help text, and action buttons are translated through dictionary keys. Dynamic filesystem paths, file names, byte counts, and protocol constants are not translated.

## Server responses

API error responses are stable English developer messages. The UI wraps them in localized context where appropriate. If API response localization becomes necessary, pass an `Accept-Language` header and map stable error codes to localized strings on the client.
